# Auditing consistent but fallible support — assessment

2026-10-13. Documentation only. **Recommend stopping at the independently accepted
comparison checkpoint.** Existing evidence demonstrates correction capability,
but does not operationally define when paying for an audit is worthwhile. No audit
policy or applicability-runtime integration is recommended for implementation now.

## Knowledge and authority in c3/r10

[Original correction contract](../experiments/CORRECTION_PROTOCOL.md),
[results](../experiments/CORRECTION_RESULTS.md), and
`outputs/correction-001/results.json` record c3's agreeing initial shield reports
true/true and payload true. The learner also has a shielded historical branch with
three successes and one failure; its fixed score is +1/3, producing success. It
does not know the hidden coordinate replacements or final failure label.

| Item | What it warrants | What it does not warrant |
| --- | --- | --- |
| Registered instrument log | This scoped report is in the allowed registry; retain its provenance | The reported value is true or statistically independent of other reports |
| Complete consistent effective support | Required active parts agree under the declared relation | Agreement establishes world truth |
| Exact correction permit | This specific payload/authority operation may be submitted | Its value is correct, useful or needed |
| Active target/digest check | Operation addresses the current head at its exact coordinate | Reference reliability or final outcome correctness |
| Independent coordinate verification | Replacement matches the supplied synthetic reference for that coordinate | A correct coordinate guarantees transmission success |
| Branch score | Fixed summary of four admitted outcomes in that branch | Calibrated probability, certainty, or a model of every cause of failure |
| Evaluator label | Subsequent scoring of the frozen prediction | Pre-action knowledge or newly authorized training evidence |

The original c3 history accepts two corrections to false/false and predicts failure
at -1/3. Intermediate heads and original reports remain inspectable. In the recent
r10 snapshot only c3-a is offered; action preflight rejects it as `already resolved`.
One admitted coordinate correction could instead expose conflict and restore
abstention. That is not the original two-correction answer under a one-request budget.
The existing receiver can revise consistent support; the current selector declines
to initiate that process. This is an authored policy boundary, not a broken ledger.

The [current action runtime](ACTION_COMMAND_RUNTIME.md) supports only r1/r8/r2,
correlated offered actions and one lifetime request. r10/c3 is not an initialized
runtime scenario. There is no audit command, general reference query or automatic
new episode. Reopening uncertainty does not replenish budget. Source/sender strings
are synthetic registration, not secure authentication or institution reliability.

## One conditional capability contract, not a recommended new study

If a concrete external audit purpose is later supplied, a separate, opt-in
**operator-requested coordinate audit** could be eligible despite resolved support:

- An explicit pre-action request names a scope and active coordinate to check. It
  must be supplied independently of evaluator outcomes and hidden replacement values.
  No request means no audit. This is an external instruction, not learned trust.
- The target must contribute to current decision support, retain fallible instrument
  provenance and have an available, exact scoped reference-check capability with
  an applicable unused correction permit. Fresh-head/digest, strict value-domain
  and budget checks still bind. Resolved support alone would not exclude this
  separate action. No policy for conflicting or missing support is silently changed.
- A frozen rule can select the uniquely requested eligible coordinate, otherwise
  abstain with a reason. Do not choose among many targets by their hidden labels,
  nationality, source name, philosophical node, or a newly invented reliability score.
- Under the existing fixture interface, the service returns a proposed replacement,
  not an independent yes/no audit result. Audit initiation therefore requests an
  already permitted correction proposal. Unchanged authorization, target and
  reference verification decide whether a replacement is admitted. An audit label
  supplies no extra right to rewrite evidence. A pure read-only reference query
  would require a different, currently absent service contract.
- Charge the one opportunity even when the proposal is rejected or uninformative;
  preserve raw reports, root ancestry, verification receipts and remaining uncertainty.
  No refund, second correction, direct truth query or reference-value leak to selection.

This could demonstrate that an explicitly requested check can revisit apparent
resolution. c3 already largely demonstrates that capability. It would not learn
when to request a check, establish net benefit or justify an always-audit default.
Ordinary memory/direct control should implement exactly the same request, target,
permit, reference, budget and receipt rules. No propagation contribution is required.

Potential future public triggers include a genuinely observed calibration failure,
known applicability expiry, a registered disagreement or an independent audit
schedule. Those would need defined semantics and evidence. They are not currently
populated signals in c3, and merely announcing an audit capability is not proof of
error or worthwhile expected information. Human reliance on institutions motivates
provenance and scope questions; it does not supply numerical reliability weights.

| Useful check | Original c2/c3 repairs expose disagreement or change the selected branch. These were authored known-error cases; c3's final failure needs two corrections. |
| Cost-only check | c11's second same-value attestation adds no independent root or new value. Its target is already reference-corrected, so it does not match the candidate's fallible-instrument eligibility. c12's irrelevant color correction likewise fails target relevance. Neither is a matched resolved, correct, audit-eligible control. |
| Misleading admitted report | c3's initially agreeing instrument reports are erroneous; existing late c1/c9 reports can restore abstention without certifying truth. This demonstrates the need to separate report admission from a reference audit, not the value of an audit policy. |
| Coordinate repair without predictive benefit | c9/r8 remains wrong after a valid reference correction. Coordinate truth does not settle the final task. |

The available useful-check examples therefore cannot select an audit default.
Creating only another known-error c3 fixture would manufacture an apparent winner.
Do not invent a cost-only or misleading-reference case just to balance a new study;
first identify the real task's feedback and audit opportunity distribution.

## Why r8 and applicability inference need different treatment

r8/c9 passes coordinate verification, then selects a historical branch that already
contains an exception. Its public inputs lack the information that separates every
success from failure. The retained [diagnosis packet](../outputs/investigation-priority-fix-handoff-001/r8-r10-read-only-diagnosis.md)
found no prediction-contract inconsistency. Auditing the same correct coordinate
does not discover a missing predictive variable. The evaluator's case-ID lookup
is not a learning feature. Blanket abstention would also suppress correct answers.

The independently accepted [applicability study](../experiments/CONTEXT_APPLICABILITY_PROTOCOL.md)
learns a second-channel interpretation from two public context bits and separately
verified raw/reference calibration pairs. It assumes the first measurement's
orientation is supplied and correct. Current action cases instead supply an authored
equal/complement relation, lack those context/calibration inputs and admit potentially
erroneous instrument reports. Agreement itself is not calibration evidence.

Thus integration is not a drop-in solution: transforming only c3's second true
measurement cannot make both observations correctly false while its first remains
true. It also cannot supply c9's missing final-outcome information. Integration could
be justified for a task that actually provides the tested calibration contract and
needs learned interpretation; no such runtime task is identified here. Do not invent
context bits from case IDs or register another runtime mode merely to reuse a module.

## Decisions versus reversible experimental details

Owner/task choices still needed: what decision justifies spending an audit budget;
whether revealing error and abstaining is valuable; which independently grounded
signals warrant a check; what the reference is trusted to establish and over what
scope; and what costs or later uses count. These are not resolved by the provisional
preference for useful partial learning.

Safe later experimental details include isolated snapshots, one fixed opportunity,
same-information memory controls, deterministic ties, immutable source/receipt
provenance, and separate information/resolution/correctness/cost measures. They do
not authorize the missing task objective or reference service.

**Single recommendation: retain the accepted checkpoint and stop.** The actual gap
is a task-grounded audit trigger and value contract, not an unimplemented correction
capability. Neither another c3 demonstration nor immediate applicability integration
currently answers it. This note proposes no experiment or production change; parent
review is next.
